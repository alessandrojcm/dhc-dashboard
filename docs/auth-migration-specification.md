# Supabase Auth to Phoenix Authentication Migration Specification

**Status:** Approved for implementation planning  
**Scope:** Replace Supabase Auth while retaining Supabase-hosted Postgres.  
**Out of scope:** Implementing the work, moving Postgres hosting, changing Membership/authorization policy, and a self-service account-management surface.

## Goal and invariants

DHC will replace Supabase Auth with Phoenix-owned authentication generated by
`mix phx.gen.auth`, using Assent for Discord OAuth. Phoenix owns principals,
external identities, magic links, and sessions; DHC continues to own Members,
Invitations, Roles, authorization, and Membership.

The migration must preserve these invariants:

- Each existing Member becomes exactly one Authentication Principal with the
  same UUID currently held in `auth.users.id`; all Member and audit foreign-key
  associations remain valid.
- A Principal exists for exactly one Member. Pending Invitations have no
  Principal. Phoenix never creates a session for a principal without current
  club access.
- A Discord account is identified by its immutable provider subject, not its
  email, username, or avatar. One provider subject and one provider-per-
  principal are each unique.
- The authoritative login email is normalized and globally unique. It is set
  from the Invitation email for new members; Discord-reported data is metadata.
- A valid Session implies current club access. Phoenix is the only
  authorization boundary; SvelteKit role checks are presentation only.
- Cutover is a planned maintenance-window, big-bang switch. No Supabase
  sessions, bearer tokens, refresh tokens, or GoTrue session state are
  migrated.

The authoritative decisions behind this specification are [Phoenix owns
authentication](adr/0009-phoenix-owns-authentication.md), [Authentication
within Invitation Acceptance](adr/0010-authentication-within-invitation-acceptance.md),
and the resolved tickets linked from [Chart the migration from Supabase
Auth](https://linear.app/alessandrojcm/issue/ALE-146/chart-the-migration-from-supabase-auth).

## Target contract

### Principal, identity, and access

- Generate the Phoenix authentication schema first and use its generated
  principal, token, and session columns. Add only the identity and
  migration-audit columns this specification explicitly requires; do not invent
  a parallel bespoke auth schema.
- Store Discord identities separately with `provider = discord`,
  `provider_subject`, `principal_id`, and JSONB metadata. Enforce unique
  `(provider, provider_subject)` and `(principal_id, provider)`.
- Import existing Discord links from Supabase's `auth.identities.provider_id`.
  Validate agreement with any payload subject fields before import. A Discord
  email, verification state, username, or avatar must never rewrite an imported
  link or the authoritative login email.
- On a new Discord callback, resolve an existing `provider_subject` first. For
  an unlinked subject, automatically link only when Discord reports a verified
  email that exactly matches one principal's login email. If it matches zero
  principals, or the principal already has Discord linked, deny the Discord
  login without disclosing account existence and offer magic link instead.
- There is no initial self-service email-change, unlink, ban, or disablement
  feature. Trusted operators may amend a normalized unique login email or remove
  an external identity directly in the database. An email change revokes all
  sessions. Existing Stripe-driven `is_active` remains the only access-loss
  mechanism.

### Login and session boundary

- Magic links are random, database-hashed, single-use tokens with a 15-minute
  expiry. Requests are non-enumerating. On consumption, delete outstanding
  magic-link tokens for the principal and create a new session.
- Sessions are random, opaque, database-backed, per-device tokens in a
  `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` cookie scoped to
  `.dublinhemaclub.com`. They have a 30-day absolute lifetime and do not slide.
  Login rotates the session; current-device logout revokes one session;
  sign-out-everywhere, login-email changes, and loss of access invalidate all.
- Phoenix checks Member existence and `is_active` when a session is created and
  on every authenticated request. Missing, expired, or ineligible sessions are
  `401`; an authenticated principal without a required role is `403`. Load
  roles from `user_roles` on every request.
- Browsers call Phoenix directly with credentials included. SvelteKit forwards
  the shared-domain cookie explicitly for SSR, server loads, and remote
  functions. Credentialed CORS permits only the dashboard origin. Mutations
  accept JSON only and require an allowed `Origin`, including explicit origin
  forwarding by SvelteKit. This is the initial CSRF boundary; do not introduce a
  separate CSRF token without a newly documented reason.
- Replace all Supabase session projections atomically with the purpose-built
  Phoenix session projection `{ principal: { id, email }, roles }`. Remove
  compatibility code for bearer access tokens, refresh tokens, `sub`, and
  `app_metadata.roles` rather than maintaining an adapter.

### Invitation Acceptance

Invitation issue inserts only the invitation (including a fresh Phoenix UUID in
`invitation.user_id`, email, date of birth, expiry, creator, and `pending`
status). It creates no profile, principal, identity, or Stripe customer.

Acceptance is registration, not login. In one `Repo.transaction`, it locks the
pending invitation and creates the Principal (using `invitation.user_id`),
`UserProfile`, `MemberProfile`, and `member` role; marks the invitation accepted;
sets `user_profile.is_active = true`; and marks any waitlist entry joined. It
does not establish a session or send a magic link. The success page directs the
new Member to normal sign-in.

The first login is a normal magic-link or Discord login. A Discord email mismatch
requires a magic-link login before authenticated linking. The invitation status
flip is the replay defence; the existing 15-minute verification token is not
single-use. Pending Invitations present at migration cutover are deleted and are
not migrated.

## Delivery slices

Each slice is ordered; do not begin a later slice until its acceptance criteria
are satisfied.

1. **Generate and model Phoenix authentication.** Run `mix phx.gen.auth` and
   adopt its generated schema/API shape. Add Assent Discord integration,
   external-identity persistence, normalized login-email constraints, session
   policy, central access/role loading, and the Phoenix session projection.
   **Accept when:** magic-link and linked-Discord sign-in create only compliant
   opaque sessions; invalid/inactive principals receive `401`; role failures
   receive `403`; no endpoint trusts a SvelteKit role check or Supabase bearer
   token.
2. **Replace the SvelteKit auth seam.** Configure direct credentialed Phoenix
   access, SSR/remote forwarding, origin checks, and session projection
   consumption. Remove Supabase client session refresh and every token/claim
   adapter.
   **Accept when:** browser and SSR dashboard requests work with the Phoenix
   cookie; cross-origin credential and mutation protections are tested; no
   production auth path invokes Supabase Auth.
3. **Move Invitation Acceptance to the target lifecycle.** Remove issue-time
   GoTrue/profile creation and make acceptance create the principal and Member
   record set atomically. Implement post-acceptance first-login behaviour and
   Discord linking rules.
   **Accept when:** issue time has one invitation insert; accepted invitations
   atomically materialize the full record set without a session; replays roll
   back; mismatched Discord login cannot mis-link; pending invitations can be
   safely deleted during cutover.
4. **Ship migration M1.** In the release pipeline, create/populate generated
   auth tables and `auth_migration_audit`. Populate one principal for every
   `user_profiles` row (including inactive Members), preserve UUIDs, and import
   Discord identities only. Leave the application on Supabase Auth.
   **Accept when:** source/target principal and Discord-identity aggregate
   reconciliation succeeds on a restored production backup rehearsal; any
   orphan, collision, inconsistent provider subject, or normalized-email
   anomaly aborts. Orphans are repaired before retry—there is no exclusion
   manifest path.
5. **Cut over with migration M2.** Under the runbook's write freeze, transactionally
   assert reconciliation, repoint all 17 foreign keys from `auth.users` to
   `principals.id`, rename `supabase_user_id` and `user_roles.user_id` to
   `principal_id`, and deploy the matching API/frontend.
   **Accept when:** the transaction proves no drift since M1, every referenced
   UUID has a Member profile, all constraints target `principals.id`, and the
   deployed application reads only the new names.
6. **Observe and retire.** Invalidate all Supabase sessions, complete production
   smoke checks, and monitor for seven days with Supabase Auth configured but
   unused. Then disable providers and retire Supabase Auth credentials.
   **Accept when:** aggregate telemetry is healthy throughout the observation
   window and the operator has recorded the audit/reconciliation evidence.

## Migration mechanics and cutover runbook

M1 and M2 are normal, transactional Ecto migrations shipped with the release;
they are not an ad hoc production script. M1 creates/populates the target tables
and audit row while Supabase Auth remains live. M2 is the cutover event: it runs
under a write freeze, asserts source/target reconciliation, repoints all 17
foreign keys, and renames the two application-facing columns. `auth.*` remains
as dead weight so M2's `down/0` can restore its foreign keys and column names;

The production sequence is: enable maintenance mode; verify and take a database
backup; deploy the Phoenix-auth API without reopening traffic; run M1/M2 and
their assertions; invalidate Supabase sessions; deploy the Phoenix-auth
frontend; execute smoke checks; reopen traffic. If a migration fails, its
transaction leaves no committed change. If it commits but the deployed
application or smoke checks fail, restore the backup and redeploy the previous
Supabase-Auth API and frontend.

Required smoke checks: magic-link sign-in; Discord sign-in for an imported,
linked Member; authorized dashboard/API access; unauthorized rejection; and first
sign-in after Invitation Acceptance. Monitor aggregate, non-personal metrics for
auth success/failure by method, link/collision failures, session-validation
failures, and reconciliation/audit mismatches.

## Test obligations

- Unit and context tests for normalized email uniqueness, identity uniqueness,
  provider-subject precedence, verified-email auto-linking, collision rejection,
  session rotation/revocation/expiry, magic-link single use and expiry, and
  central access/role outcomes.
- Transaction tests for Invitation Acceptance: all records commit together;
  failure rolls all back; no session is minted; replay is rejected; inactive
  Members cannot mint sessions; pending invitations are not carried through the
  migration.
- Ecto migration tests and restored-backup rehearsal covering M1/M2, all 17 FK
  repoints, UUID preservation, active and inactive Members, Discord imports,
  expected audit rows, and abort/rollback on each anomaly class.
- API/contract tests for `401` versus `403`, Phoenix session projection,
  credentialed CORS, allowed-Origin mutations, and absence of bearer-token
  compatibility.
- End-to-end production-like tests for both login methods, direct browser and
  SSR requests, existing-Member continuity, post-invitation first login, and
  cutover rollback rehearsal.

## Operational controls and open implementation risks

Before implementation begins, the delivery owner must turn these controls into
concrete operational configuration and runbooks:

- Magic-link sender/domain, rate limits, anti-enumeration response, delivery
  failure handling, and secrets for email and Discord OAuth.
- Secret storage and rotation for cookie signing, magic-link tokens, Discord
  credentials, and the retired Supabase credentials during the observation
  window.
- Alert thresholds, dashboard ownership, audit-evidence retention, backup
  restore ownership, and the exact maintenance-mode communication.
- The generated `phx.gen.auth` schema shape and its upgrade implications. The
  implementation must adapt this specification to the actual generator output,
  not alter it to fit assumed columns.
- Payment idempotency if a Stripe charge survives an acceptance transaction
  rollback. This is a pre-existing onboarding concern and must be handled by
  its owning implementation work before altering the acceptance transaction.
