# ADR 0009: Phoenix owns authentication

**Status:** Accepted  
**Date:** 2026-07-17  
**Deciders:** @alessandrojcm  
**Tags:** authentication, phoenix, ecto, oauth, discord

## Context

DHC is replacing Supabase Auth while retaining Discord OAuth and email magic-link login. Existing Members must keep their association without re-registration, Invitations remain the only path to membership, and DHC must own the authentication user directory in its Postgres database.

Hosted identity providers such as Clerk own the user directory and therefore do not meet the ownership requirement. Better Auth stores users locally, but would split authentication behavior into SvelteKit, request authentication into Phoenix, and schema ownership into Ecto. Pow and PowAssent provide a Phoenix-native framework and account linking, but Pow does not provide DHC's required passwordless magic-link login as a first-class flow and would place the application behind a slower-moving runtime abstraction.

Phoenix 1.8's `mix phx.gen.auth` generates editable, application-owned magic-link authentication code. Assent provides the Discord OAuth protocol and a maintained `Assent.Strategy.Discord` without taking ownership of users, sessions, or application policy.

## Decision

Phoenix owns authentication using code generated by `mix phx.gen.auth`, with Assent providing Discord OAuth.

- Ecto migrations own authentication principals, tokens, sessions, and external-identity tables in DHC's Postgres database.
- DHC Invitations remain the only way to establish an authentication principal and Member association; public self-signup is not supported.
- The invitation email is authoritative. A Discord identity may be explicitly linked to an authenticated principal even when Discord reports a different email.
- A failed or absent Discord link does not prevent access; the member continues to use magic-link login.
- Discord's immutable provider subject is the identity key. Capturing and displaying the current Discord username is a separate onboarding enhancement and does not block the authentication migration.
- DHC roles, authorization, Membership, and Member data remain outside the authentication module.
- The SvelteKit-to-Phoenix session and request-authentication contract will be specified separately.

## Consequences

- DHC owns the user directory, schema, migration history, identity links, sessions, and exit path.
- Invitation acceptance and authentication-principal creation can participate in Phoenix/Ecto transactions rather than crossing runtimes.
- Authentication and authorization tests stay in the Phoenix test harness; SvelteKit only tests its client integration.
- DHC must maintain the generated authentication code and review relevant changes in future Phoenix generators.
- DHC must implement the external-identity schema, Discord callback/linking policy, and the session contract used by SvelteKit.
- Assent handles OAuth protocol details, but DHC remains operationally responsible for magic-link delivery, abuse controls, secret rotation, monitoring, and recovery policy.

## Alternatives considered

- **Clerk or Auth0.** Rejected because the provider owns the authentication user directory.
- **Better Auth.** Rejected because it would keep the stateful authentication runtime in SvelteKit/Cloudflare while Phoenix and Ecto become authoritative for the rest of the backend.
- **Pow and PowAssent.** Rejected because their account-linking advantage does not offset custom magic-link work, framework coupling, additional session-cache concerns, and slower recent PowAssent maintenance.
- **Phoenix authentication without an OAuth library.** Rejected because implementing the OAuth protocol directly adds avoidable security-sensitive work; Assent already supplies the Discord strategy.
