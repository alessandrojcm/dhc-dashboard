# Google Calendar sync for Workshops — research

**Research date:** 2026-11-03  
**Question:** Can the Phoenix application sync Beginners' Workshops and regular
Workshops to the club's Google Workspace Calendar, then send Google Calendar
invitations to paid people?

**Subsequent design interview:** [the design draft](../google-calendar-workshop-sync-design.md)
records the user's decisions, including separate committee/participant calendars
and organizer-account OAuth rather than domain-wide delegation. The alternatives
and open policy questions below describe the research stage; the design document
owns the later decisions. This research does not authorize implementation.

## Conclusion

Yes. Google Calendar API v3 supports a club-owned event, explicit attendee
membership, attendee invitation/update/cancellation emails, event rescheduling,
and caller-supplied event IDs. The practical Phoenix choice is a small
`Req`-based Calendar REST adapter plus an authentication-token provider; there
is **not** a currently maintained official Elixir Calendar client to adopt.

For the intended club-owned shared calendar *and* Google invitations to people
whose email may be outside the Workspace domain, prefer a dedicated Workspace
organizer account and one of these credentials:

1. **Recommended if a Workspace super-admin will approve it:** service account
   with narrowly scoped domain-wide delegation (DWD), impersonating that
   organizer account. This is unattended and preserves a stable human/club
   organizer. Google explicitly requires DWD for service accounts to populate
   `attendees[]`.
2. **Lower admin privilege, but with an operational credential:** a one-time
   OAuth consent flow for the dedicated organizer account, storing its encrypted
   refresh token. `access_type=offline` enables background refresh. This does
   not need DWD, but the club must maintain/re-consent the organizer credential
   if it is revoked.

Do **not** use an un-delegated service account merely shared onto a calendar
when invitations are required: Google documents that such a service account
needs DWD to populate the attendee list. A shared calendar may still be a good
place to publish club events, but it does not remove that attendee restriction.

Sources: [Events resource — attendees](https://developers.google.com/workspace/calendar/api/v3/reference/events#resource),
[Google service-account OAuth](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority),
[web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server#offline).

## Elixir library status

### Google-maintained generated client

`google_api_calendar` was the Calendar package generated by the
Google-owned [`googleapis/elixir-google-api`](https://github.com/googleapis/elixir-google-api)
repository. Its README describes generated clients and names `Goth` as its
authentication companion. However, the repository was **archived by its owner
on 2026-06-30**, its README says it is no longer actively maintained and
experimental, and it explicitly says it is not an officially supported Google
product. It is therefore not a suitable new production dependency.

Google's current server-side OAuth client-library list has no Elixir entry.
Calendar v3 is a documented JSON/HTTP API, so using the repository's sanctioned
`Req` client directly is a small, controlled alternative rather than adopting
an abandoned generated client.

Sources: [Google APIs Elixir repository](https://github.com/googleapis/elixir-google-api),
[Google web-server OAuth client-library list](https://developers.google.com/identity/protocols/oauth2/web-server#libraries),
[`apps/phoenix/mix.exs`](../../apps/phoenix/mix.exs) (existing `Req`; no Google
Calendar or Goth dependency).

### Goth

[`goth`](https://github.com/peburrows/goth) is a community package by Phil
Burrows, **not Google-maintained**. It is an authentication/token package, not
a Calendar API client. Its current source supports both
`{:service_account, credentials}` and `{:refresh_token, credentials}` sources,
caches access tokens, and refreshes them before expiry. It could supply the
bearer token for a thin Calendar adapter, including the refresh-token route;
it does not create/update Calendar events itself. Its default HTTP client is
Finch, whereas this repository's HTTP policy is Req outside documented seams;
using Goth would need an intentional exception or a configured client function.

Sources: [Goth README](https://github.com/peburrows/goth#readme),
[Goth source (`Goth.start_link/1`)](https://github.com/peburrows/goth/blob/master/lib/goth.ex),
[`apps/phoenix/AGENTS.md`](../../apps/phoenix/AGENTS.md).

## Calendar operations and notification semantics

### Club event lifecycle

| Domain change | Calendar operation | Required notification choice |
| --- | --- | --- |
| Create/publish a workshop | `events.insert` on the club calendar, with the workshop's deterministic event ID | `sendUpdates=none` while no attendees exist; `all` if attendees are included at creation |
| A person becomes eligible for invitation | Update the authoritative attendee set on the event | `sendUpdates=all` to send the invitation/update |
| A person ceases to be eligible | Update the authoritative attendee set without that address | decide whether `all` should notify the removed guest; Google exposes the same parameter on update |
| Venue/time/title/description reschedule | `events.update` (full resource) or `events.patch` (only changed fields) | `sendUpdates=all` if guests must be notified |
| Club cancellation | `events.delete` | `sendUpdates=all` if guests must receive the cancellation |

`events.insert`, `events.update`, `events.patch`, and `events.delete` all take
`sendUpdates` values `all`, `externalOnly`, or `none`. `all` sends to all
guests; `externalOnly` sends only to non-Google-Calendar guests. The API says
some email can still be sent even when notifications are disabled; it warns
that `none` during insertion can cause external-calendar sync loss or events
to be lost. Thus `sendUpdates` is an API notification instruction, not an
exactly-once email-delivery guarantee.

Adding attendees means supplying `attendees: [%{email: ...}]`; email is
required for a new attendee. The event resource confirms new invitations should
use `needsAction`. When an array field is supplied to `patch`, it replaces the
whole array; `update` replaces the complete event resource. Consequently, the
adapter must read/persist the full intended attendee set rather than patching a
single email into a stale list. `attendeesOmitted` is only appropriate for a
participant updating their own response, not for organizer-side roster sync.

Sources: [Create events guide](https://developers.google.com/workspace/calendar/api/guides/create-events),
[insert reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert),
[update reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/update),
[patch reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch),
[delete reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete),
[Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events#resource).

### Calendar invitation versus an email carrying ICS

An API invitation is the Calendar API operation above: the organizer creates
one event, adds `attendees[]`, and asks Google to send updates. The attendee can
accept or reject it, and subsequent organizer updates and cancellation operate
on that same Calendar event. Automatic appearance on a guest's calendar is not
guaranteed: their invitation settings may require responding to the invitation
email first, particularly for an unknown sender.

An application email with an `.ics` attachment is a separate mail-delivery
design, not an `events.insert`/`attendees[]` Calendar integration. An attachment
alone does not create or maintain the attendee roster on the club's Google
event. This is not a claim that standards-based calendar email cannot support
updates or cancellations; that would be a separate integration design. An ICS
attachment alone should not be represented as “Google Calendar invitations
sent” in the product contract.

Sources: [Calendar sharing — invite users to an individual event](https://developers.google.com/workspace/calendar/api/concepts/sharing),
[insert reference — attendee response status and invitation settings](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert).

### Idempotency and reconciliation

Set an event ID at insert time, derived deterministically from the local
workshop's immutable ID and a namespace/prefix. Google permits caller-supplied
IDs that are unique per calendar, use lowercase base32hex (`a-v`, `0-9`), and
are 5–1024 characters. Google specifically says this keeps local entities in
sync and prevents duplicate creation after an ambiguous successful insert.
Store the chosen event ID and calendar ID durably; do not use `iCalUID` as a
substitute, because their semantics differ.

For Google-side edits/deletions, decide whether the system is one-way
authoritative or reconciles changes. The Calendar API supports full plus
incremental event synchronization via a persisted `nextSyncToken`; an expired
or invalid token returns 410 and requires discarding the local synced copy and
performing a new full sync. The recommendation is initially one-way ownership:
DHC owns workshop facts and attendee eligibility, while the calendar event is
a projection. Add inbound sync only if staff are meant to edit the Google event
or attendees there.

Sources: [Create events guide — event IDs](https://developers.google.com/workspace/calendar/api/guides/create-events),
[Events resource — `id` and `iCalUID`](https://developers.google.com/workspace/calendar/api/v3/reference/events#resource),
[incremental sync guide](https://developers.google.com/workspace/calendar/api/guides/sync).

### Privacy

Set `visibility: "private"` for person-facing workshop events when the shared
calendar should not reveal their details. Google says private event details are
visible only to users with at least `writer` calendar access. Set
`guestsCanSeeOtherGuests: false` to avoid guests seeing the attendee list;
also explicitly set `guestsCanInviteOthers: false` and
`guestsCanModify: false` rather than relying on defaults. Calendar ACLs remain
material: sharing and the attendee's own calendar-sharing configuration affect
what others can see.

Sources: [Calendar sharing and visibility](https://developers.google.com/workspace/calendar/api/concepts/sharing),
[Events resource — guest controls and visibility](https://developers.google.com/workspace/calendar/api/v3/reference/events#resource).

## Fit with the two local domains

This is a projection from two distinct authoritative domains, not a shared
Workshop table:

* **Regular Workshops:** `Dhc.Workshops.Workshop` supplies title, description,
  location, UTC start/end and lifecycle status. `Registration` has
  `pending`, `confirmed`, `cancelled`, and `refunded`; both pending and
  confirmed hold a place. The existing cancellation command fan-outs refunds
  under the payment boundary. The report does **not** infer which local status
  should receive an invitation; “paid” must be defined at the payment boundary
  and made an explicit Calendar projection policy.
* **Beginners' Workshops:** `BeginnersWorkshop` stores a Dublin civil `date`
  and `start_time`; `Dhc.ClubCalendar` is the approved conversion owner.
  `Intake` is separate from ordinary registration and has `contacted`, `paid`,
  attendance, lapse/return/defer/cancellation states, including payment by
  Stripe or carried fee. Reschedule keeps people and places intact and already
  sends a domain email to each open Intake; cancellation turns paid people into
  deferred/held-credit outcomes and contacted people into returned ones. A
  Calendar projection must listen after the boundary commits and must use the
  same conversion/facts, never independently recompute dates or payment
  eligibility.

## Recommended design direction (not implementation)

1. Create one club calendar and a dedicated Workspace organizer identity.
2. Use DWD impersonation of that identity if the administrator approves the
   limited Calendar scope; otherwise use that identity's encrypted OAuth refresh
   token. Enable the Calendar API and give the identity write access to the
   chosen calendar.
3. Introduce one Phoenix-owned Calendar projection boundary that takes a
   *closed, minimal* workshop event shape and authoritative attendee email set.
   It should own event-ID generation, Google request/response translation,
   token use, retry/reconciliation records, and notification choice. Existing
   payment/workshop boundaries remain the source of truth and enqueue/signal it
   only after their transaction commits.
4. Use one deterministic Google event per local workshop; update it for
   reschedules; delete it with `sendUpdates=all` only when policy says to cancel
   guests. Reconcile failed outbound work rather than making Calendar calls
   inside payment/lock transactions.
5. Only add an eligible person to `attendees[]` after the agreed paid/confirmed
   transition; use `sendUpdates=all`. Maintain the roster as a full desired set
   and deliberately process removals.

This aligns with the repo's existing HTTP preference for `Req`, its strict
workshop command boundaries, and its rule that the frontend never becomes
authoritative for payment state.

## Deliberately undecided business policy

This research does **not** decide any of the following, and no implementation
was made:

* Whether regular-Workshop `pending` or only `confirmed`/completed payment
  receives an invitation, including zero-price places.
* Whether Beginners' Workshop Stripe-paid and carried-fee-paid Intakes are
  equivalent for invitations; whether a deferred/held workshop credit keeps,
  loses, or transfers a Calendar invite.
* Whether cancellation/refund, decline, lapse, withdrawal, no-show, or an
  attendee's payment reversal removes an attendee or cancels the whole event;
  nor whether those transitions email a Calendar update.
* Whether staff edits in Google Calendar are prohibited, overwritten, or
  synchronized back; whether invitations should go to external email addresses;
  retention/deletion rules for attendee emails and Calendar IDs; event copy,
  calendar visibility/ACL policy, reminders, or Google Meet use.
* Whether the Workspace administrator is willing to grant DWD, which scopes
  they approve, or whether operational ownership of an OAuth refresh token is
  acceptable. Google documents that a Workspace super-admin must authorize DWD
  and scopes in Admin Console; this is an administrative prerequisite, not a
  code-level decision.

Source: [Google service-account domain-wide delegation setup](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority).
