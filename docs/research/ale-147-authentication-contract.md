# ALE-147 — Current authentication contract

**Research date:** 2026-07-17  
**Question:** What authentication data, identity links, claims, session behavior, request validation, and invitation-acceptance paths must a replacement preserve or deliberately change?

## Executive summary

The current contract is still Supabase Auth, not Phoenix-owned auth. Supabase's immutable `auth.users.id` is the cross-system principal identifier: `user_profiles.supabase_user_id`, `user_roles.user_id`, `user_audit_log.user_id`, `invitations.user_id`, and `invitations.created_by` reference it; `member_profiles.id` also references it as its primary key. [`supabase/migrations/20241113174153_users_schema.sql:28-52`](../../supabase/migrations/20241113174153_users_schema.sql#L28-L52), [`apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs:14-15,73-92`](../../apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs#L14-L15), [`apps/phoenix/priv/repo/migrations/20260512000005_create_member_profiles.exs:5-10`](../../apps/phoenix/priv/repo/migrations/20260512000005_create_member_profiles.exs#L5-L10), [`apps/phoenix/priv/repo/migrations/20260512000009_create_invitations.exs:6-19`](../../apps/phoenix/priv/repo/migrations/20260512000009_create_invitations.exs#L6-L19)

Supabase JWTs require `sub`; authorization depends on `app_metadata.roles`, injected from `public.user_roles` by `custom_access_token_hook`. SvelteKit validates the JWT through Supabase `getUser()`, stores/refreshes Supabase session cookies, and sends the access token as a Bearer token to the API. Phoenix currently validates those same Supabase tokens and exposes normalized claims as `conn.assigns.current_user`. [`supabase/migrations/20241113174153_users_schema.sql:116-219`](../../supabase/migrations/20241113174153_users_schema.sql#L116-L219), [`src/hooks.server.ts:11-63`](../../src/hooks.server.ts#L11-L63), [`src/routes/+layout.svelte:22-30,46-66`](../../src/routes/+layout.svelte#L22-L30), [`apps/phoenix/lib/dhc/auth/supabase_jwt.ex:1-31`](../../apps/phoenix/lib/dhc/auth/supabase_jwt.ex#L1-L31), [`apps/phoenix/lib/dhc_web/plugs/require_auth.ex:18-29,43-49`](../../apps/phoenix/lib/dhc_web/plugs/require_auth.ex#L18-L29)

Invitation acceptance is intentionally separate from authenticated-dashboard access. A public SvelteKit page fetches a PII-safe invitation view, verifies email plus date of birth, receives an opaque 15-minute verification cookie, and then submits that token with next-of-kin and Stripe confirmation data. Phoenix performs the public verify/accept flow; acceptance atomically activates the profile, creates the member state, marks the invitation accepted, and rolls back if payment or member creation fails. [`src/routes/(public)/members/signup/[invitationId]/+page.server.ts:9-35`](../../src/routes/(public)/members/signup/[invitationId]/+page.server.ts#L9-L35), [`src/routes/(public)/members/signup/[invitationId]/data.remote.ts:14-54,60-123`](../../src/routes/(public)/members/signup/[invitationId]/data.remote.ts#L14-L54), [`apps/phoenix/lib/dhc_web/router.ex:48-57`](../../apps/phoenix/lib/dhc_web/router.ex#L48-L57), [`apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs:415-547`](../../apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs#L415-L547)

The accepted replacement direction is Phoenix-generated authentication plus Assent for Discord, with DHC-owned principals, sessions, tokens, and external identities. The session and request-authentication boundary is explicitly still unspecified. [`docs/adr/0009-phoenix-owns-authentication.md:16-35`](../adr/0009-phoenix-owns-authentication.md#L16-L35)

## 1. Principal data and stable identifiers

### Supabase-owned identity

- The application treats `auth.users.id` as a UUID principal. The local Phoenix `Dhc.Auth.AuthUser` schema deliberately maps only `id` and `email`, is read-only, and says Supabase Auth remains the sole writer. [`apps/phoenix/lib/dhc/auth/auth_user.ex:1-31`](../../apps/phoenix/lib/dhc/auth/auth_user.ex#L1-L31)
- The migration's application profile is keyed separately by `user_profiles.id`, but its unique `supabase_user_id` points to `auth.users(id)`. The profile carries application identity and membership-adjacent data: names, active flag, DOB, phone, pronouns/gender, medical conditions, social-media consent, customer ID, and optional waitlist link. [`supabase/migrations/20241113174153_users_schema.sql:28-37`](../../supabase/migrations/20241113174153_users_schema.sql#L28-L37), [`apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs:14-32,49-56`](../../apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs#L14-L32)
- Existing members must not be re-associated by email. The project’s migration research explicitly requires an immutable mapping from the old `auth.users.id` to the replacement principal; it also notes that a replacement provider need not use the Supabase UUID natively if DHC retains that mapping. [`docs/auth-provider-comparison.md:7-16`](../auth-provider-comparison.md#L7-L16)
- `member_profiles.id` is the same UUID domain as `auth.users.id` (primary-key FK), while `member_profiles.user_profile_id` points to the application profile. This means a replacement must preserve both the auth-principal/member ID relationship and the profile relationship. [`apps/phoenix/priv/repo/migrations/20260512000005_create_member_profiles.exs:5-10`](../../apps/phoenix/priv/repo/migrations/20260512000005_create_member_profiles.exs#L5-L10)

### Provider metadata and fields actually relied upon

- Phoenix’s read-only auth schema relies only on Supabase `id` and `email`; no provider metadata or Discord subject is currently modeled in application tables. [`apps/phoenix/lib/dhc/auth/auth_user.ex:3-12,21-28`](../../apps/phoenix/lib/dhc/auth/auth_user.ex#L3-L12)
- SvelteKit uses `session.user.user_metadata` only for PostHog identification metadata. The authentication contract does not otherwise establish a stable application meaning for that object. [`src/routes/+layout.svelte:46-63`](../../src/routes/+layout.svelte#L46-L63)
- The current source does not show a persisted Discord provider subject, provider username, or external-identity table. This is a material migration gap, not evidence that Discord identity data is unimportant: ADR 0009 says the replacement must use Discord’s immutable provider subject as the identity key, while displaying the current username is optional. [`docs/adr/0009-phoenix-owns-authentication.md:20-25`](../adr/0009-phoenix-owns-authentication.md#L20-L25)
- `auth.users.email` is used by invitation conversion logic and the read-only Phoenix schema. Invitation lookup accepts either the auth user ID or the auth email, but the migration decision says the invitation email is authoritative when Discord reports a different email. [`supabase/migrations/20250316135748_invitation_system.sql:169-218`](../../supabase/migrations/20250316135748_invitation_system.sql#L169-L218), [`docs/adr/0009-phoenix-owns-authentication.md:20-24`](../adr/0009-phoenix-owns-authentication.md#L20-L24)

## 2. Foreign keys and authorization data

- `user_roles.user_id` references `auth.users.id` with `ON DELETE CASCADE` and enforces uniqueness per `(user_id, role)`. `role_type` currently contains `admin`, `president`, eleven committee/coordinator roles, `coach`, and `member`. [`supabase/migrations/20241113174153_users_schema.sql:6-23,38-43`](../../supabase/migrations/20241113174153_users_schema.sql#L6-L23), [`apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs:66-82`](../../apps/phoenix/priv/repo/migrations/20260512000004_create_users_and_roles.exs#L66-L82)
- `user_audit_log.user_id`, `invitations.user_id`, `invitations.created_by`, and invitation-processing logs’ `user_id` all reference the Supabase principal. Invitation rows additionally link to `waitlist_id`, hold status (`pending`, `accepted`, `expired`, `revoked`), expiry, type, and JSON metadata. [`supabase/migrations/20241113174153_users_schema.sql:46-52`](../../supabase/migrations/20241113174153_users_schema.sql#L46-L52), [`supabase/migrations/20250316135748_invitation_system.sql:9-24`](../../supabase/migrations/20250316135748_invitation_system.sql#L9-L24), [`apps/phoenix/priv/repo/migrations/20260512000009_create_invitations.exs:6-25,44-59`](../../apps/phoenix/priv/repo/migrations/20260512000009_create_invitations.exs#L6-L25)
- The custom access-token hook refuses a token when the user has no `user_profiles` row, reads roles from `user_roles`, and writes them into `claims.app_metadata.roles`. A replacement must either preserve this claim shape during cutover or update every SvelteKit/Phoenix consumer together. [`supabase/migrations/20241113174153_users_schema.sql:132-161,182-204`](../../supabase/migrations/20241113174153_users_schema.sql#L132-L161)
- SvelteKit decodes `app_metadata.roles` locally and applies route-level role sets. Phoenix applies role intersection in request pipelines; the role sets are not identical for every capability. For example, inventory writes are `quartermaster/admin/president`, while authenticated inventory reads are available to any authenticated member. [`src/lib/server/roles.ts:5-16,45-53`](../../src/lib/server/roles.ts#L5-L16), [`src/hooks.server.ts:102-123`](../../src/hooks.server.ts#L102-L123), [`apps/phoenix/lib/dhc_web/router.ex:36-46,124-179`](../../apps/phoenix/lib/dhc_web/router.ex#L36-L46), [`apps/phoenix/lib/dhc_web/plugs/require_auth.ex:43-46`](../../apps/phoenix/lib/dhc_web/plugs/require_auth.ex#L43-L46)

## 3. JWT, SvelteKit session, cookies, and API request behavior

### JWT contract

- Phoenix requires an HTTP `Authorization` header with `Bearer ` (or lowercase `bearer `), verifies the token using `Supabase.Auth.get_claims/3`, requires a non-empty `sub`, exposes `email`, extracts `app_metadata.roles`, and retains the raw claims. [`apps/phoenix/lib/dhc_web/plugs/require_auth.ex:18-39,49-57`](../../apps/phoenix/lib/dhc_web/plugs/require_auth.ex#L18-L39), [`apps/phoenix/lib/dhc/auth/supabase_jwt.ex:10-31,52-69`](../../apps/phoenix/lib/dhc/auth/supabase_jwt.ex#L10-L31)
- Missing/invalid tokens return 401; a valid token lacking a required role returns 403 with `Insufficient role`. The tests also pin rejection of Basic auth, an empty Bearer token, and a second header that tries to rescue a leading non-Bearer header. [`apps/phoenix/lib/dhc_web/plugs/require_auth.ex:22-31,51-65`](../../apps/phoenix/lib/dhc_web/plugs/require_auth.ex#L22-L31), [`apps/phoenix/test/dhc_web/plugs/require_auth_test.exs:64-123`](../../apps/phoenix/test/dhc_web/plugs/require_auth_test.exs#L64-L123)
- The Phoenix verifier currently falls back between JWKS/auth-server validation through the Supabase library and reads `SUPABASE_URL`, `SUPABASE_ANON_KEY`, or service-role configuration. This is transitional infrastructure, not a Phoenix-owned token contract. [`apps/phoenix/lib/dhc/auth/supabase_jwt.ex:3-8,36-49`](../../apps/phoenix/lib/dhc/auth/supabase_jwt.ex#L3-L8), [`apps/phoenix/config/runtime.exs:138-145`](../../apps/phoenix/config/runtime.exs#L138-L145)

### SvelteKit session and cookie contract

- Every server request creates a request-scoped Supabase SSR client from `PUBLIC_SUPABASE_URL` and `PUBLIC_SUPABASE_ANON_KEY`, reads all request cookies, and writes refreshed cookies with `path: "/"`. [`src/hooks.server.ts:11-38`](../../src/hooks.server.ts#L11-L38)
- `safeGetSession()` first obtains the session, then calls `getUser()` so the JWT is validated; validation failure is treated as no session. The auth guard places session/user in `event.locals`, redirects unauthenticated `/` and `/dashboard` requests to `/auth`, and redirects authenticated `/auth` users to `/dashboard`. Public routes bypass these guards. [`src/hooks.server.ts:40-63,76-100`](../../src/hooks.server.ts#L40-L63)
- The root layout serializes the session and all cookies to layout data. On the browser it creates a Supabase browser client, reads the session, listens for auth state changes, invalidates `supabase:auth` when expiry changes, and redirects on `SIGNED_OUT`. [`src/routes/+layout.server.ts:3-12`](../../src/routes/+layout.server.ts#L3-L12), [`src/routes/+layout.ts:13-58`](../../src/routes/+layout.ts#L13-L58), [`src/routes/+layout.svelte:46-66`](../../src/routes/+layout.svelte#L46-L66)
- API calls obtain `session.access_token` and send it as the client’s auth token. A replacement must provide an equivalent token acquisition/refresh boundary or intentionally change the generated API client integration. [`src/routes/+layout.svelte:22-30`](../../src/routes/+layout.svelte#L22-L30)
- Magic-link login calls Supabase `signInWithOtp` and targets `/auth/callback?next=/dashboard`; Discord login calls Supabase `signInWithOAuth({ provider: "discord" })` with the same callback. The callback exchanges the code for a session and redirects to the requested path. [`src/routes/auth/data.remote.ts:15-50`](../../src/routes/auth/data.remote.ts#L15-L50), [`src/routes/auth/callback/+server.ts:4-25`](../../src/routes/auth/callback/+server.ts#L4-L25)
- Invitation-specific cookies are separate from the authenticated Supabase session: verification is HttpOnly, `SameSite=Lax`, secure outside development, and expires after 15 minutes; the confirmation marker lasts 30 days with the same flags. Successful acceptance deletes those cookies and also deletes an `access-token` cookie, although the current flow does not otherwise establish that cookie. [`src/routes/(public)/members/signup/[invitationId]/data.remote.ts:35-53,118-123`](../../src/routes/(public)/members/signup/[invitationId]/data.remote.ts#L35-L53)

## 4. Invitation acceptance paths

There are two related but distinct paths:

1. **Invitation creation/delivery:** admin-only API routes require `president`, `admin`, or `committee_coordinator`; Phoenix queues bulk processing, creates/updates an invited profile, inserts a pending invitation, and sends the invitation email through the worker path. [`apps/phoenix/lib/dhc_web/router.ex:8-10,71-78`](../../apps/phoenix/lib/dhc_web/router.ex#L8-L10), [`apps/phoenix/lib/dhc_web/controllers/invitations_controller.ex:219-263`](../../apps/phoenix/lib/dhc_web/controllers/invitations_controller.ex#L219-L263), [`apps/phoenix/lib/dhc/invitations/repository.ex:48-79,82-115`](../../apps/phoenix/lib/dhc/invitations/repository.ex#L48-L79)
2. **Public acceptance:** the invitation page exposes only safe status/type/expiry data; the user proves possession/knowledge with invitation email + DOB; Phoenix returns a signed/opaque verification token; the browser keeps it in the short-lived HttpOnly cookie; acceptance consumes it alongside payment and membership data. [`apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs:415-470`](../../apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs#L415-L470), [`apps/phoenix/lib/dhc_web/controllers/invitations_controller.ex:88-170`](../../apps/phoenix/lib/dhc_web/controllers/invitations_controller.ex#L88-L170)

Acceptance preserves these invariants in tests: successful payment creates member state, activates the profile, leaves the `member` role, marks the invitation accepted, and changes a linked waitlist entry to `joined`; payment failure leaves the invitation pending/profile inactive/no member; invalid payload and member-creation failure also leave state uncommitted. [`apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs:471-628`](../../apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs#L471-L628)

The older Supabase SQL contract adds important edge cases that a replacement should consciously preserve or retire: invitations are unique per user, pending invitations for an email are expired before a new one, `get_invitation_info` rejects banned users and existing members, expired invitations become `expired`, and completed/invited waitlist users may receive an automatically-created 30-day workshop invitation. [`supabase/migrations/20250316135748_invitation_system.sql:75-128,169-286`](../../supabase/migrations/20250316135748_invitation_system.sql#L75-L128), [`supabase/migrations/20250326172500_invitation_system_enhancements.sql:4-18,40-117,243-307,320-368`](../../supabase/migrations/20250326172500_invitation_system_enhancements.sql#L4-L18)

## 5. Preserve versus deliberately change

### Preserve unless an explicit cutover decision says otherwise

- Stable principal mapping from every existing `auth.users.id` to the replacement principal; never infer member identity from email. [`docs/auth-provider-comparison.md:11-16`](../auth-provider-comparison.md#L11-L16)
- Invitation email authority, invitation-only principal creation, no public self-signup, and magic-link fallback when Discord is absent or cannot be linked. [`docs/adr/0009-phoenix-owns-authentication.md:20-24`](../adr/0009-phoenix-owns-authentication.md#L20-L24)
- Discord immutable subject as the external identity key, with an explicit collision/linking policy; current Discord username is not a stable identifier. [`docs/adr/0009-phoenix-owns-authentication.md:22-25`](../adr/0009-phoenix-owns-authentication.md#L22-L25)
- Role vocabulary and authorization outcomes, including 401 versus 403, while deciding whether the `app_metadata.roles` JWT claim remains during a staged migration. [`supabase/migrations/20241113174153_users_schema.sql:6-23`](../../supabase/migrations/20241113174153_users_schema.sql#L6-L23), [`apps/phoenix/lib/dhc_web/plugs/require_auth.ex:22-29`](../../apps/phoenix/lib/dhc_web/plugs/require_auth.ex#L22-L29)
- SvelteKit’s refresh/session lifecycle and a browser-to-Phoenix request credential that can be refreshed/revoked without exposing provider secrets to SvelteKit. [`src/hooks.server.ts:40-63`](../../src/hooks.server.ts#L40-L63), [`docs/adr/0009-phoenix-owns-authentication.md:30-35`](../adr/0009-phoenix-owns-authentication.md#L30-L35)
- Public invitation verification and acceptance semantics, including short-lived HttpOnly proof, PII-safe public lookup, payment-before-commit behavior, and rollback guarantees. [`src/routes/(public)/members/signup/[invitationId]/data.remote.ts:35-53,81-123`](../../src/routes/(public)/members/signup/[invitationId]/data.remote.ts#L35-L53), [`apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs:471-628`](../../apps/phoenix/test/dhc_web/controllers/invitations_controller_test.exs#L471-L628)

### Explicitly unresolved or deliberate-change decisions

- The exact SvelteKit-to-Phoenix session format, cookie domain/path/SameSite policy, refresh/revocation behavior, and whether Phoenix receives a cookie or bearer token are not specified. ADR 0009 explicitly defers this contract. [`docs/adr/0009-phoenix-owns-authentication.md:25-35`](../adr/0009-phoenix-owns-authentication.md#L25-L35)
- The replacement external-identity schema and migration procedure for Discord provider subjects are not implemented. The current repository has no persisted provider-subject model in the reviewed auth/profile schemas; this needs a deliberate import/linking plan. [`apps/phoenix/lib/dhc/auth/auth_user.ex:21-31`](../../apps/phoenix/lib/dhc/auth/auth_user.ex#L21-L31), [`docs/adr/0009-phoenix-owns-authentication.md:30-35`](../adr/0009-phoenix-owns-authentication.md#L30-L35)
- It is undecided whether the replacement should retain Supabase-compatible `sub`, `email`, and `app_metadata.roles` claims for a transition window or change Phoenix/SvelteKit/API-client consumers atomically. The current code has consumers in both runtimes. [`src/lib/server/roles.ts:5-15`](../../src/lib/server/roles.ts#L5-L15), [`apps/phoenix/lib/dhc/auth/supabase_jwt.ex:10-30`](../../apps/phoenix/lib/dhc/auth/supabase_jwt.ex#L10-L30)
- The legacy invitation email template still points at a local Supabase Auth invite verification URL, while the active public page uses Phoenix `/api/invitations/:id/verify` and `/accept`. This indicates a stale/dead delivery path or an unfinished migration that must be resolved before cutover. [`supabase/templates/invite.html:5-10`](../../supabase/templates/invite.html#L5-L10), [`apps/phoenix/lib/dhc_web/router.ex:53-56`](../../apps/phoenix/lib/dhc_web/router.ex#L53-L56)
- The current source does not show an explicit magic-link callback handler beyond Supabase’s generic `/auth/callback`, nor a separate provider-linking flow. Phoenix must own those flows under ADR 0009, including delivery, abuse controls, secret rotation, and recovery policy. [`src/routes/auth/callback/+server.ts:4-25`](../../src/routes/auth/callback/+server.ts#L4-L25), [`docs/adr/0009-phoenix-owns-authentication.md:30-35`](../adr/0009-phoenix-owns-authentication.md#L30-L35)

## Validation and source limits

This is a source-only inventory; no authentication code was changed. Sources reviewed were the SvelteKit hooks/layout/auth/invitation paths, Supabase migrations/templates/pgTAP tests, Phoenix auth plug/verifier/router/invitation code and tests, and first-party project guidance/ADR documents. No live Supabase instance or production auth data was queried, so actual provider metadata values, current user population, token signing algorithm/key rotation, and production cookie attributes remain unverified.
