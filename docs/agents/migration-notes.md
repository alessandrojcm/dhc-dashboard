# Migration notes

Notes governing the active migration from SvelteKit + Supabase to Phoenix + Ecto + Oban. AGENTS.md is an index; the detail lives here.

## Database

- **Ecto owns all schema changes.** Supabase migrations frozen. Baseline migrations model current schema in Elixir code. Before first Phoenix/Fly release migration on an existing Supabase DB, run `bridge.sql` once to seed Ecto `schema_migrations` for the Supabase-backed baseline only; leave Oban/new cutover migrations pending. The bridge is mirrored into `supabase/seed.sql` so a local `pnpm supabase:reset` auto-seeds `schema_migrations` and leaves the DB ready for `mix ecto.migrate` (which then runs only the cutover migrations: `20260512000001` Oban + `20260611224011` pg_cron removal). The standalone `scripts/bridge.sql` remains for one-shot production use via `psql "$DATABASE_URL" -f scripts/bridge.sql`.
- **Baseline migration fixes**: The testcontainers harness (ADR 0006) was the first time the baseline Ecto migrations actually ran against a fresh DB. This surfaced and fixed several latent bugs in the initial `4e5430e1` migration set: (1) `20260512000004` used `add :id, :bigint, default: fragment("generated by default as identity")` — invalid SQL (`DEFAULT "generated..."`); replaced with raw `CREATE TABLE` using `GENERATED BY DEFAULT AS IDENTITY`. (2) `20260512000004` relied on `add :supabase_user_id, ..., unique: true` — but Ecto silently ignores `:unique` on `add/3` (only `:default`/`:null`/`:collation` are emitted); added an explicit `create unique_index(:user_profiles, [:supabase_user_id])` (required by the FK in `20260512000008`). (3) `20260512000006` and `20260512000008` created both a `unique_index` and a plain `index` on the same column — name collision; dropped the redundant plain indexes. (4) `20260512000006` and `20260512000010` seeded rows via raw `INSERT` missing the timestamp columns (NOT NULL from `timestamps/1`); added `NOW(), NOW()`. (5) `20260512000007` & `20260512000008` (workshop tables), `20260512000006` (`settings`), and `20260512000010` (`inventory_*`) used plain `timestamps(type: :timestamptz)` producing `inserted_at`, while production Supabase uses `created_at`/`updated_at` — all fixed to `timestamps(type: :timestamptz, inserted_at: :created_at)`. This is now enforced structurally by the `elixir-timestamps-missing-created-at` ast-grep rule (run via `mise run ast-lint`; see `sgconfig.yml`). See [critical-patterns.md](critical-patterns.md) "Timestamp column names" for the rule and [anti-patterns.md](anti-patterns.md) for the forbidden inverse. Safe for production (`bridge.sql` marks baselines applied; they only re-run in the testcontainers harness).

## Auth / RLS

- **Auth target (ADR 0009, ALE-156)**: Supabase Auth is temporary. Replace it with Phoenix-owned authentication generated by `mix phx.gen.auth`; use Assent for Discord OAuth. Preserve Supabase UUIDs as DHC principal IDs and model provider identities separately. Phoenix owns opaque 30-day sessions in a shared `.dublinhemaclub.com` `Secure`/`HttpOnly`/`SameSite=Lax` cookie; browser clients call Phoenix with `credentials: 'include'`, while SvelteKit server and remote-function requests forward the cookie. Phoenix checks `isActive` and live roles on every request. Cut over SvelteKit atomically to a Phoenix session projection rather than preserving Supabase claims or bearer tokens. Invitations remain the only principal-creation path, the invitation email is authoritative, and a missing or mismatched Discord link falls back to magic-link login. The production cutover sequence remains to be specified.
- **ALE-165 (Phoenix magic-link foundation, in progress)**: The first Phoenix-owned authentication path is live alongside the transitional Supabase-JWT path. `principals` + `principal_tokens` tables (migration `20260719120000_create_phoenix_auth_tables.exs`) store DHC-owned login identities, magic-link tokens (`context = "login"`, 15-min, single-use, SHA-256-hashed), and opaque DB-backed session tokens (`context = "session"`, 30-day absolute, hashed). The `Dhc.Auth` context owns magic-link issue/consume, session create/revoke, and the `load_session_principal/1` access projection (joins `user_profiles`/`user_roles` by UUID equality — the post-M1 invariant `principals.id == auth.users.id == user_profiles.supabase_user_id`; ALE-163 tightens this to a real FK after the rename). `DhcWeb.Plugs.RequireSession` is the Phoenix-session counterpart of `RequireAuth`: 401 for missing/expired/inactive, 403 for missing role. `DhcWeb.Plugs.MagicLinkRateLimit` enforces 3/email/15min and 10/IP/hour with a non-enumerating 200 body, backed by the `auth_rate_limit_windows` table. Routes: `POST /api/auth/magic-link` (public, rate-limited), `POST /api/auth/magic-link/verify` (public, sets the signed `_dhc_session` cookie), `GET /api/auth/session` + `DELETE /api/auth/session` (`:authenticated_session_api`). Magic-link delivery enqueues a `Dhc.Email.Worker` job with the `"magicLink"` friendly name (resolved to a Loops transactional ID via `MAGIC_LINK_TRANSACTIONAL_ID`, provisioned in `fnox.toml`). Aggregate, non-personal telemetry: `[:dhc, :auth, :magic_link, :requested|:succeeded|:failed|:inactive_principal|:rate_limited]` and `[:dhc, :auth, :session, :rejected]`. No PII or token material in logs. Existing endpoints are unchanged and still on `RequireAuth`; ALE-163 will repoint them to `RequireSession` under the cutover.
- **ALE-164 (dashboard Supabase auth seam replaced with Phoenix Sessions, in progress)**: The dashboard authenticates through the Phoenix `_dhc_session` cookie. No Supabase client, session refresh, bearer-token forwarding, or JWT-role extraction remains on the production dashboard auth path. **Phoenix side**: `DhcWeb.Plugs.RequireAuth` (the transitional Supabase-JWT plug that still guards the data API until ALE-163) now accepts the signed `_dhc_session` cookie as an alternative to the bearer token, preferred when both are present. The cookie path produces the same `current_user` shape controllers already read (`sub`, `email`, `roles`) via `Dhc.Auth.load_session_principal/1`, so no controller changes were required. `GET /api/auth/socket-token` (`:authenticated_session_api`) exchanges the cookie for a short-lived, DB-backed, JS-readable socket token (`principal_tokens.context = "socket"`, 60s, SHA-256-hashed) — the browser cannot read the HTTP-only cookie to pass it as the Phoenix JS `authToken`, and `new WebSocket(url, protocols)` has no `withCredentials` so a cross-origin socket cannot send the cookie. `DhcWeb.UserSocket.connect/3` accepts the socket token (decoded from Base64) in addition to the Supabase JWT; `DhcWeb.NotificationChannel` accepts a `notifications:self` topic alias (the browser cannot read its own id from the opaque token) resolved to the verified `sub`. **Dashboard side**: `src/hooks.server.ts` replaces the Supabase server client + `auth.getUser()` JWT-validation seam with a credentialed call to Phoenix `GET /api/auth/session` via `getPhoenixSession(cookies)` (`src/lib/server/auth.ts`). `App.Locals` drops `supabase`/`user`/the Supabase `Session` shape; `session` is now the Phoenix session projection `{ principal: { id, email }, roles }`. `src/lib/server/roles.ts` reads roles from the projection, not JWT `app_metadata.roles`. `src/lib/server/api-client.ts` `apiClientOptions(cookies)` forwards the `_dhc_session` cookie via the `cookie` header for SSR/server-load/remote-function calls; the browser uses `configureClient({ credentials: "include" })`. The auth page (`src/routes/auth/`) posts to Phoenix `/api/auth/magic-link`; the magic-link email points at `/auth/magic-link?token=<token>` whose server load consumes the token at Phoenix `/api/auth/magic-link/verify` and forwards the `Set-Cookie` to the browser. The Discord button is disabled (ALE-167 re-enables via Assent). `src/routes/dashboard/+layout.svelte` logout calls `DELETE /api/auth/session`; `NotificationCenter` + `notification-realtime.svelte.ts` fetch a socket token via `authSocketToken()` (credentialed) and pass it as `authToken`. The OpenAPI spec gained `AuthSession` tag + `cookieSession` security scheme + `AuthSessionProjection` schema; the generated `@dhc/api-client` re-exports `authRequestMagicLink`/`authVerifyMagicLink`/`authShowSession`/`authDeleteSession`/`authSocketToken`. **Tests**: `apps/phoenix/test/dhc_web/plugs/require_auth_session_cookie_test.exs` (cookie path + precedence + 401/403), `apps/phoenix/test/dhc_web/channels/user_socket_test.exs` (socket-token path), `apps/phoenix/test/dhc_web/channels/notification_channel_test.exs` (`notifications:self` join), `apps/phoenix/test/dhc_web/controllers/auth_session_controller_test.exs` (`GET /api/auth/socket-token`), `src/lib/server/auth.test.ts` (SSR seam), `src/lib/components/notifications/notification-realtime.test.ts` (socket-token bridge), `e2e/ale-164-phoenix-session-auth.spec.ts` (browser + SSR + signed-out redirect + rejected-origin CORS).
- **ALE-162 (Invitation Acceptance is the Principal lifecycle, in progress)**: Acceptance is now the atomic registration event (ADR 0010, slice 3 of `docs/auth-migration-specification.md`). Migration `20260719181022_ale_162_drop_auth_users_fks_add_invitation_acceptance_columns.exs` drops the four `auth.users` FK constraints (`invitations.user_id`, `user_profiles.supabase_user_id`, `user_roles.user_id`, `member_profiles.id`) and the `invitations.user_id` unique index, and adds nullable `first_name`/`last_name`/`phone_number`/`date_of_birth`/`stripe_customer_id` columns to `invitations`. The rename + FK repoint to `principals.id` is **not** done here — that is M2 / ALE-163 under a write freeze; columns stay named as-is. Issue time is now side-effect free: `Dhc.Invitations.BulkInviteWorker` no longer calls the Supabase admin API, creates a Stripe customer, or inserts a `user_profiles` row; it mints a fresh Phoenix UUID for `invitation.user_id`, stores the invite data (first/last/phone/DOB) on the invitation row, enqueues the `inviteMember` email, and marks the waitlist `invited`. `Dhc.Invitations.Repository.create_invitation_record/3` no longer takes `user_id`/`customer_id`; `Dhc.UserProfiles.Repository` (`upsert_invited_profile/4`) was removed as dead code. `Dhc.Invitations.verify_credentials/3` now matches email + DOB directly on the invitation (no `user_profiles` join). `Dhc.Invitations.Pricing.pricing_for_invitation/2` lazily creates a Stripe customer on first preview and persists it on `invitations.stripe_customer_id` (reused on subsequent pricing calls and by acceptance). `Dhc.Invitations.accept/5` rewrites the acceptance transaction: it locks the invitation `FOR UPDATE`, reuses `invitation.stripe_customer_id` or creates a Stripe customer (via the new `Dhc.Invitations.StripePayment.create_customer/4`), runs `StripePayment.complete/1`, then creates the `Principal` (`Auth.register_principal_with_id/2` with `id = invitation.user_id`), `UserProfile`, `MemberProfile`, `member` role, flips the invitation to `accepted`, sets `user_profile.is_active = true`, and marks the waitlist `joined` — all committing together. Acceptance does **not** create a Session or send a magic link; the new Member signs in through the normal magic-link/Discord path. Failed or replayed acceptance leaves no partial record set (the invitation-status flip is the replay defense; the verification token is not single-use). Tests: `invitations_controller_test.exs` and `bulk_invite_worker_test.exs` rewritten to the new flow (no Supabase/Stripe Bypass; `insert_invitation_with_profile/1` no longer creates `auth.users`/`user_profiles`; acceptance tests assert the Principal + UserProfile + MemberProfile + role are created atomically, no session/login tokens, and rollback leaves nothing). Full suite: 636 passed. Frontend contract unchanged (OpenAPI DTOs unchanged; only descriptions updated). Pending invitations at cutover are deleted (ADR 0010), so the new invitation columns are nullable and not backfilled.
- **RLS**: No new policies. Existing ones removed when PostgREST is disabled.

## Workshops

- **Workshop RBAC drift**: The original `club_activity_registrations` RLS policy granted `beginners_coordinator` full registration visibility (carried forward in the combined `20250804190122` policy), corrected to `workshop_coordinator` by `20250923100806_fix_workshops_rls.sql`. Phoenix coordinator Workshop reads (calendar, attendees/refunds) must use `workshop_coordinator`/`president`/`admin` and must NOT reproduce the old `beginners_coordinator` policy. See the `Dhc.Workshops` moduledoc.
- **Member Workshop API**: `GET /api/workshops` is the member-facing Workshop collection. It is authenticated-only, defaults/constrains `status` to `planned,published`, returns counts plus current-user interest/registration state, and intentionally does not expose attendee identities or `club_activity*` join shapes. `src/routes/dashboard/my-workshops/+page.svelte` consumes it through `@dhc/api-client` rather than browser Supabase PostgREST.

## Inventory

- **Inventory Phoenix REST contract (ALE-104)**: Inventory migration uses Phoenix/OpenAPI camelCase payloads even though persistence remains snake_case (`availableAttributes`, `parentContainerId`, `outForMaintenance`, `totalPages`, etc.). Authenticated members may read Inventory resources; `quartermaster`, `president`, and `admin` may write. Preserve current behavior during migration: category/container deletes conflict while referenced, item `PATCH` accepts `categoryId` because the current service does even though the UI does not expose category changes, item deletion is exposed in the API, and item history stays on separate `/history` endpoints rather than embedded in item detail.
- **Inventory Phoenix implementation**: Inventory categories, containers, items, history, commands, and dashboard statistics are Phoenix-owned. Svelte consumes the generated `@dhc/api-client`; it must not query inventory tables directly. Reuse `Dhc.Inventory.JsonArray` for jsonb columns that store arrays (`available_attributes`) because Ecto's built-in `:map` rejects lists. The camelCase↔snake_case boundary lives in controllers/renderers. Raw SQL touching `auth.users` must qualify the table (`INSERT INTO auth.users`, not `prefix: "auth"` on `Repo.query`). RBAC remains split between `:authenticated_api` reads and `:inventory_admin_api` (`quartermaster`/`president`/`admin`) writes.

## Queues / Oban

- **Queues**: pgmq → Oban. Big-bang per-queue cutover. Discord → Email → Announcements → Stripe → Bulk Invite.
- **Loops transactional email**: `Dhc.Email.Worker` (queue `:emails`, `max_attempts: 5`) sends via the Loops.so REST API (`POST https://app.loops.so/api/v1/transactional`) using a hand-rolled `Req.post/2` adapter — no Swoosh/Bamboo. Job args carry a **friendly name** (`inviteMember`/`workshopAnnouncement`/`workshopRegistration`/`workshopRegistrationError`); the worker translates it to the real Loops dashboard ID via the `:loops_transactional_ids` app-env map (built in `config/runtime.exs` + `config/dev.exs` from the `INVITE_MEMBER_TRANSACTIONAL_ID`/`WORKSHOP_ANNOUNCEMENT_TRANSACTIONAL_ID`/`WORKSHOP_REGISTRATION_TRANSACTIONAL_ID`/`WORKSHOP_REGISTRATION_ERROR_TRANSACTIONAL_ID` env vars, all provisioned in `fnox.toml`). This mirrors the edge function's env-var lookup. Only `workshopRegistration` has a real Loops ID as its fallback default (`cmnok76cq02tq0ix92oeoi1kk`); the other three **must** be set in prod or the worker fails fast with `{:error, {:transactional_id_not_configured, name}}` — it never sends the friendly name to Loops (that produces a 404 after 5 retries, as seen in Sentry DHC-API-16). Producers: `Dhc.WorkshopAnnouncements.Worker` (fans out 1 email job per active member), `Dhc.Invitations.BulkInviteWorker` + `Dhc.Invitations.resend_invitation_emails/1` (enqueue `inviteMember` per invite).
- **Worker logging convention**: Every Oban worker log line carries the job context as keyword metadata (`oban_job_id`, `oban_attempt`, `oban_queue`, `oban_worker`) plus domain-specific keys (`email`, `transactional_id`, `loops_id`, `loops_status`, `workshop_id`, `announcement_type`, `created_by`, `invitation_id`, etc.). These keys are registered in three places that must stay in sync when adding new metadata: (1) `config :logger, :default_formatter, metadata: [...]` in `config/config.exs` (local logs), (2) `config :sentry, logs: [metadata: [...]]` in `config/config.exs` + `config/runtime.exs` (Sentry Logs), (3) `Sentry.LoggerHandler` `metadata: [...]` in `config/runtime.exs` (Sentry error events from Logger). `Sentry.capture_message/2` in this Sentry version (13.1.0) does **not** accept `:contexts` — pass Oban context via `:extra` as a flat map. To avoid Sentry PII redaction (`reason: [Filtered]`) on error tuples that contain emails, pass reasons through a `reason_to_map/1` helper that stringifies keys/values rather than `inspect/1`.

## API design / clients

- **API design**: Spec-first with OpenAPI. Custom Mix task generates Phoenix controller stubs. TypeScript client generated from spec.
- **PostgREST read migration**: Replace SvelteKit `supabase.from(...).select(...)` reads with domain-shaped Phoenix APIs, not table/view proxies. Track remaining call sites in [postgrest-read-migration.md](postgrest-read-migration.md); first slice is Waitlist per ADR 0005.
- **`.remote.ts` files**: The swap point. Rewrite from `executeWithRLS()` to `fetch(apiClient)` per domain.

## Capability migration plan

- **Svelte service → Phoenix capability migration**: Use `src/lib/server/services/` as the behavioral inventory, but do not port service classes 1:1. Migrate for capability parity and reshape boundaries in Phoenix around domain language. Current agreed low→high complexity and recommended delivery order: Settings → Inventory → Waitlist / Onboarding Intake → Members / Membership → Invitations / Onboarding Conversion → Workshops. Track implementation complexity separately from operational risk. Stored procedures are absorbed into the owning capability (for example `insert_waitlist_entry` into Onboarding Intake and `complete_member_registration` into Invitation Acceptance), not migrated as a standalone DB-function cleanup track. Workshop migration should use vertical slices for internal/API testing, but remain Svelte-owned until full capability parity is ready to switch over.
- **Supabase Edge Functions are retired**: Do not add `supabase/functions` or call `supabase.functions.invoke(...)`. Bulk invitations use `POST /api/invitations`; email, Discord, announcements, and Stripe synchronization run in Oban; Stripe webhooks enter through Phoenix at `POST /api/webhooks/stripe`.
- **GitHub deployment workflows**: `.github/workflows/deploy-master.yml` no longer deploys Supabase Edge Functions. Do not reintroduce `supabase functions deploy`; edge-function replacements live in Phoenix/Oban. The remaining Supabase CLI job is only for `supabase/migrations/**` changes.

## Ecto gotchas

- **Ecto schema inserts vs raw SQL**: The seed tasks and test fixtures insert via the Ecto schemas (`MemberProfile`, `UserProfile`, etc.), not `Repo.insert_all` with raw maps. Two gotchas surfaced by this: (1) `member_profiles.preferred_weapon` is a Postgres `preferred_weapon[]` enum array, but the schema declares it `{:array, :string}` — inserts work because Postgres implicitly casts `text[]` → `preferred_weapon[]` at the column boundary (no custom Ecto type needed). (2) `MemberProfile`'s `:utc_datetime` fields reject microseconds; any computed `DateTime` must be `DateTime.truncate(dt, :second)` before insert (Postgres `timestamptz` accepts microseconds, so the old raw SQL didn't need this).

## Stripe

- **Stripe API**: Generated from Stripe OpenAPI spec via `oapi_generator`. Custom processor allows only needed endpoints. Regenerate with `mise run stripe-gen`. Hand-written `Dhc.Stripe.Client` adapter delegates to `Req`. API version pinned in `:stripe_api_version` config (default `"2025-10-29.clover"`) and sent as `Stripe-Version` header — must match `src/lib/server/stripe.ts`.
- **Stripe webhooks**: Phoenix controller validates Stripe-Signature header (HMAC-SHA256 via `Dhc.Stripe.Webhook`) then enqueues `Dhc.StripeWebhooks.Worker`. Raw body required — `DhcWeb.CacheBodyReader` caches `conn.assigns[:raw_body]` before JSON parsing. Webhook signing secret via `STRIPE_WEBHOOK_SIGNING_SECRET` env var (supports list for rotation). Endpoint is unauthenticated (`POST /api/webhooks/stripe`).

## Test harness

- **Test harness**: Phoenix tests are driven by testcontainers-elixir via the root `docker-compose.yml` (`db` profile only). No `supabase start` required. `test_helper.exs` owns the full lifecycle (`--no-start` alias stops Mix from auto-starting the app): start `:hackney` (testcontainers-elixir's Tesla adapter needs it; not in its extra_applications) → start compose `db` profile → read the dynamic host port via `ComposeEnvironment.get_service_port/3` → merge hostname/port into the static Repo config from `config/test.exs` → start `:ecto_sql`/`:postgrex` and run migrations under a throwaway Repo supervisor → stop it → `Application.ensure_all_started(:dhc)` (Oban's `verify_migrated!` passes because `oban_jobs` now exists) + `:bypass` → sandbox + ExUnit → `System.at_exit` stops the app then runs `docker compose down -v` (testcontainers-elixir defaults `remove_volumes: true`). Migrations run BEFORE the app, not after — ADR 0006 line 11 assumed the reverse, but Oban 2.23's `testing: :manual` still runs `verify_migrated!` at startup, so `oban_jobs` must exist first. `config/test.exs` reads `POSTGRES_PASSWORD`/`POSTGRES_DB` from the same `.env` that interpolates the compose `db` service (defaults to `postgres`/`postgres`). The `supabase/postgres:17.6.1.136` image ships the `auth` schema + `pg_jsonschema` as *available* (not installed); migration `20260512000002` runs `CREATE EXTENSION IF NOT EXISTS pg_jsonschema WITH SCHEMA extensions`. E2E still uses `supabase start` for now; the compose file's `supabase` profile (GoTrue/Kong/PostgREST) is reserved for a future E2E migration. See ADR 0006.
