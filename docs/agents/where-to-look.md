| Create a notification that must not duplicate on retry | `apps/phoenix/lib/dhc/notifications.ex` (`create_keyed/3`, `create_keyed_in_transaction/3`, `signal_created/1`) + `apps/phoenix/lib/dhc/notifications/notification.ex` (`notification_key`) + migration `20260911142515_ale_287_keyed_notifications.exs` + `apps/phoenix/test/dhc/notifications_test.exs` | ALE-287. `create/2` is at-least-once and stays that way for existing unkeyed callers; **any caller in a retryable context (Oban job, resubmittable command) must use `create_keyed/3`**. `create_keyed/3` refuses an open transaction because it signals after its own commit. A caller that already holds locks inserts with `create_keyed_in_transaction/3` (refuses *outside* a transaction so a missed signal cannot look like a create) and calls `signal_created/1` only after the outer `Repo.transaction` returns `{:ok, _}`. The key names the *logical event*, never the recipient — uniqueness is `(principal_id, notification_key)` in the DB, so one event notifies a borrower and every operator from one key. Returns `{:ok, :created \| :already_created}` so a caller with its own side effect can tell whether it was the creator; a duplicate is a normal outcome, never a `Postgrex.Error`. It broadcasts **only** on `:created` (re-signalling makes a suppressed write look like new activity) and never updates the existing row (that would resurrect a notification the recipient already read). Writes go through `insert_all` because `Repo.insert` + `on_conflict: :nothing` cannot report whether the row landed — the schema autogenerates its `binary_id` in Elixir. `read_at` is stamped in Postgres as `GREATEST(now(), created_at)`: truncating an Elixir clock rounded *below* `created_at` and 500'd `mark_read` on the newest notification. |
