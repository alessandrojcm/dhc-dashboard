| Change target Inventory Item availability (move, maintenance, archive) | `apps/phoenix/lib/dhc/inventory/operator_item_lifecycle.ex` (commands) + `apps/phoenix/lib/dhc/inventory/item_projection.ex` (label + availability) + `apps/phoenix/lib/dhc/inventory/item_guards.ex` (item locking, dependency checks) + `apps/phoenix/test/dhc/inventory/operator_item_lifecycle_test.exs` | ALE-294 (284b). Availability is **always** a projection of open maintenance plus approved/checked-out loans — never a stored flag, and never the legacy `out_for_maintenance` column. Movement is its own command (allowed in maintenance, blocked by a live loan) and never a general edit. Maintenance is retained periods with at most one open per item; archive replaces deletion once history exists and ends an open period atomically. Every command locks the item `FOR UPDATE` first, so interlocks queue per item and losers get a domain conflict (`:loan_active`, `:maintenance_open`, `:archived`) rather than an exception. Loan commands themselves are ALE-286. |
| Expose target Inventory Items over the API | `apps/phoenix/lib/dhc_web/controllers/inventory_operator_items_controller.ex` + `inventory_operator_items_json.ex` + `apps/phoenix/lib/dhc/inventory/operator_item_list.ex` (paginated read) + `apps/phoenix/priv/api/openapi.yaml` (`Inventory` tag) + `apps/phoenix/test/dhc_web/controllers/inventory_operator_items_controller_test.exs` + `inventory_operator_items_client_parity_test.exs` | ALE-295 (284c). Each command is its own route/request schema so the generic PATCH carries only `notes`/`values`. `list_operator_items/1` orders on the immutable slug with an `id` tie-break, returns exact `COUNT(*)`, and binds cursors to every filter. |
| Add member-facing Inventory catalog or own-loan behavior | `apps/phoenix/lib/dhc/inventory/member_catalog.ex` (browse/search/filters) + `apps/phoenix/lib/dhc/inventory/member_loans.ex` (request, cancel, own history) + `apps/phoenix/lib/dhc/inventory/club_calendar.ex` (Europe/Dublin today) + `apps/phoenix/lib/dhc_web/controllers/inventory_catalog_controller.ex` + `inventory_member_loans_controller.ex` (+ their `_json.ex`) | ALE-285. **A separate read model, never a role variant of the operator viewer.** Member rows are plain maps carrying only label, slug, category, values, and a generic availability reason (`available`/`on_loan`/`maintenance`), so no field added to `Item` or its projection can leak to a member by default (story 45). Availability still comes from `ItemProjection`, so member and operator views cannot disagree. Archived items are absent with no filter to opt into, and an archived slug answers `:not_found` rather than "archived". Container path is disclosed only from approval onward, on the member's own loan (story 15). Members request only for themselves — there is no borrower parameter. Loan commands take the item `FOR UPDATE` **before** the loan, matching `OperatorItemLifecycle`; the reverse order deadlocks against approval. Operator transitions and the shared queue are ALE-286; notifications/reminders are ALE-287 and deliberately absent here. |
| Add operator loan transition behavior | `apps/phoenix/lib/dhc/inventory/operator_loans.ex` (approve, reject, operator cancel, checkout, return, date edits) + `apps/phoenix/lib/dhc/inventory/club_calendar.ex` (`today/0`, `on_date/1`) + `apps/phoenix/test/dhc/inventory/operator_loans_test.exs` | ALE-296 (286a). The operator half of the lifecycle; the member half stays in `MemberLoans` and is never duplicated here. **Operator cancel applies only to an `approved` loan** — a pending request is rejected, and after checkout release is a return. Approval is the single decision point: it reserves the item, rejects every competing pending request with a system note, and snapshots the container path (approval is the collection entitlement, story 15). Checkout is gated to the approved window in club-calendar days with the item out of maintenance; an early or late handover edits the dates *first* rather than widening the window. Start is immutable at checkout; due stays editable but may never precede `checked_out_at` (ALE-273). Overdue is derived, never stored. Unlike the member's cancel, approve/checkout/return are **not** idempotent — each has an allocation or custody effect the caller must be able to attribute. The queue is ALE-297 (286b); contracts, routes, and notifications are 286c and blocked on ALE-287. |
| Read the shared operator loan queue | `apps/phoenix/lib/dhc/inventory/operator_loan_queue.ex` + `apps/phoenix/test/dhc/inventory/operator_loan_queue_test.exs` | ALE-297 (286b). A **read model**, not a command surface: no locks, no notifications, and no actor parameter — the queue is shared with no claim, assignment, or ownership semantics, so every duty officer sees the same thing (story 50). Four buckets, each `%{count: n, rows: [...]}` where `count` is `length(rows)`: one query loads every open loan and partitions it in memory, so a count can never disagree with the rows beside it — which is also why the queue is deliberately unpaginated. `handovers_due` holds every approved loan whose start has arrived, *including* one whose window has lapsed, with a per-row `ready_for_checkout?` so real work never falls through; a future-dated approval is in no bucket. Returns and overdue share one bucket because getting the item back is one action and overdue is only derived urgency on it. Rows are `OperatorLoans.operator_view/2` verbatim (public for exactly this reason), so a queue row and the detail read cannot disagree; `ClubCalendar.today/0` is resolved once per queue. Labels and availability come batched from `ItemProjection`, never per row. `ready_for_checkout?` is advisory — `check_out_loan/3` re-decides under the item lock, which is what makes a stale `true` safe. Contract and exposure are 286c. |
