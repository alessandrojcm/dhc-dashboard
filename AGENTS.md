# PROJECT KNOWLEDGE BASE

**Status:** Phoenix + Ecto + Oban migration complete

## Overview

Dublin Hema Club dashboard monorepo: the SvelteKit 3.x + Svelte 5 frontend lives in `apps/web`, alongside the Phoenix + Ecto + Oban backend in `apps/phoenix`. Root pnpm/mise commands delegate to the frontend workspace, which consumes Phoenix through the typed OpenAPI client in `packages/api-client`.

Invitation Acceptance is owned by `Dhc.Onboarding.Acceptance` (GH-507) behind an **opaque handle** — the signed `_dhc_onboarding_acceptance` cookie value — and every browser-facing operation returns a closed safe view whose `state` is the discriminator; never return an Ecto schema, attempt id, operation token, confirmation token, or provider subject from it. Every authoritative read of Continuation/Attempt/Invitation/Claim rows goes through `Acceptance.Locked` (principal advisory → subject advisory → Continuation → Attempt → Invitation → Claims): add a transition inside a `with_locked`/`lock!` block rather than writing a new `FOR UPDATE` query. Synchronous `submit_payment/2`, explicit `retry/1`, and worker `recover/1` converge on the private `progress/2` (lease in one transaction, Stripe outside it, `owned_fence!/1` before every write) — do not add a second Stripe progression path. Pricing is handle-bound too (`preview_pricing/2`, `GET /onboarding/invitation-acceptance/pricing`, `paymentReady` only per ADR-0019): the public Invitation id is never workflow authority, so do not reintroduce an `/invitations/:id/pricing`-style read. `Dhc.Onboarding` keeps only Invitation-level operations. See the Invitation Acceptance row in `docs/agents/where-to-look.md`.

The SvelteKit half of Invitation Acceptance (GH-509, ADR 0024) is one boundary too: `apps/web/src/lib/server/invitation-acceptance/` owns the frontend's interpretation of Phoenix's safe-view `state`, the route outcomes, and the cookie effects those outcomes request; `apps/web/src/lib/invitation-acceptance/` holds the shared status vocabulary, presentation, and the component-scoped `paymentMachine`. Routes and remote functions under `routes/(public)/members/signup/[invitationId]/` are thin adapters — build `invitationAcceptanceDeps(cookies)`, run one workflow operation, then `applyInvitationRouteOutcome` for a route outcome or `applyRouteEffects` for a command outcome that answers the form with data (verification, payment failure) — and must not branch on `response.data.state` or touch the `_dhc_onboarding_acceptance` cookie directly. XState v5 is used two ways and only two: the server decision machine runs through the pure `initialTransition`/`transition` functions (never a module-scope actor; SvelteKit server modules are shared across requests), and browser actors are created per component with `@xstate/svelte`'s `useMachine`. XState snapshots are never authoritative; Phoenix is. See the Invitation Acceptance frontend row in `docs/agents/where-to-look.md`.

Workshop express checkout (GH-512) is a second component-scoped browser machine: `workshop-checkout-machine.ts` owns the Stripe/registration protocol and stage-aware retry (a completion failure must not create a new PaymentIntent). Stripe objects stay in `workshop-express-checkout.svelte`; do not persist a snapshot. Membership reactivation stays on TanStack Query. See the workshop express checkout row in `docs/agents/where-to-look.md`.

JavaScript/TypeScript linting uses the shared root Oxlint config through the `apps/web` and `packages/api-client` workspace scripts; formatting uses Oxfmt from `apps/web`. Root `pnpm` and mise tasks delegate to those workspace scripts.

Frontend data flow has a few owning modules, each documented under "Remote Forms" and "TanStack Query with the Phoenix API" in `docs/agents/critical-patterns.md`: one Valibot schema per form in `lib/schemas/` (built from `fields.ts`; output is the generated request body; dates stay `YYYY-MM-DD` strings), `apiProblem` in `lib/api-error.ts` for every Phoenix error (`detail`/`code`/`fields`), `inventoryCommand` for quartermaster remote forms, `lib/inventory/member-loans.svelte.ts` for member Loan transitions, and `createCursorTableUrl` for URL-backed cursor tables. Runes controllers (`*.svelte.ts`) are tested as `*.svelte.browser.test.ts` because the unit project runs Svelte's server build; see "SvelteKit (current)" in `docs/agents/notes.md`.

SvelteKit 3 conventions the type checker does not catch: imports are `#lib/...` subpath imports with explicit file extensions, env vars are declared in `apps/web/src/env.ts` and read from `$app/env/*`, every remote-form control name must come from `field.as(...)` (a plain `name=` — including a named bits-ui Select/RadioGroup — rejects the whole submission), and external redirects need `{ external: true }`. See "Remote Forms" in `docs/agents/critical-patterns.md` and "SvelteKit (current)" in `docs/agents/notes.md`.

Frontend UI is one vocabulary too: `apps/web/src/lib/components/ui/` (shadcn-svelte) owns every interactive primitive, so a button, input, select, checkbox, radio group, dialog, sheet, label-and-error trio, or empty state is composed from a component there — `NativeSelect` when the native dropdown is what you want, `date-picker.svelte` for a date field — and a missing primitive is added from the registry rather than hand-styled native markup. Feature code never imports `bits-ui` directly. See "UI: `#lib/components/ui` Owns Every Interactive Primitive" in `docs/agents/critical-patterns.md` for the substitution table and the add command.

Authorization is one capability vocabulary (GH-510, ALE-344): **Phoenix works out capabilities** in `Dhc.Auth.Capabilities` — the only module that knows role sets — and gates routes with `plug RequireSession, capability: :"x.y"` in pipelines named after the capability (the router names no roles). Owner-scoped capabilities (`members.profile.*`) are checked in the controller and hide the resource from a non-owner with 404. The session projection carries `capabilities`; the frontend boundary `apps/web/src/lib/server/authorization/` exposes `authorizationFor(session)` → `{ can, decide, require, navigation }` and the hook adapter `guardRoute`, and applies only ownership and navigation on top of `session.capabilities` — it has no role names, and feature code must not read roles. To gate something new, add the capability to `Capabilities`, the `AuthCapability` OpenAPI enum and `RULES` in `capabilities.ts`, then reference it from the router pipeline, the nav definition, the protected-route rules (SvelteKit route ids, segment-aware), and the route load. Phoenix stays authoritative. See the authorization row in `docs/agents/where-to-look.md`.

HTTP hardening has a few owning seams. Use `DhcWeb.Plugs.ClientIp` for client IPs (never `conn.remote_ip`), because SvelteKit calls Phoenix server-side with a shared-secret `x-dhc-client-ip`. The `:api` pipeline accepts JSON bodies only. Credential-bearing email variables are sealed, and Web Push endpoints are allowlisted. See "HTTP Hardening Seams" in `docs/agents/critical-patterns.md`.

Phoenix `mix precommit` runs `hex.audit` before dependency-provided Mix tasks; under the pinned Mix version, running Credo or Reach first unloads the archived Hex task from the current process.

HTTP errors have one renderer (ALE-343): controllers declare `action_fallback DhcWeb.<Domain>HTTP` and return `{:error, reason}` or a changeset; the domain module (`use DhcWeb.Problem, reasons:, fields:`) owns status and detail, and `code` appears only on 409/422 reasons. Never `put_status`/`json(%{errors: …})` an error in a controller; plugs use `DhcWeb.Problem.send_reason/2`. See "HTTP Errors" in `docs/agents/critical-patterns.md`.

Dev data can include pending direct member invitations through `mise run seed-invitations [count]` and representative inventory through `mise run seed-inventory [item-count]`; see the Seeds section in `docs/agents/commands.md` for all seed tasks.

Waitlist Status (ALE-375) is a standing in the queue — `waiting | removed | attended | invited | joined` — and changes **only** through `Dhc.Waitlist.change_standing/2`, which runs inside the caller's transaction, locks the entry, and refuses any change outside the `Dhc.Waitlist.Standing` table. Never write `waitlist.status` directly (the E2E harness seed is the one deliberate exception), and do not re-add a status field to `PATCH /waitlist/entries/:id`, which edits admin notes only. See the Waitlist standing row in `docs/agents/where-to-look.md`.

Waitlist entry and direct Invitations are duplicate-proof (ALE-376): Waitlist registration and the staff "add a new person" path (`Dhc.Waitlist.add_person/2`, which Fast-track will call inside its transaction) share one refusal set — `:email_on_waitlist`, `:email_is_principal`, `:email_has_pending_invitation` — that the public endpoint hides and the staff path returns. Every Invitation is issued through `Dhc.Onboarding.issue_invitation/3` inside the caller's transaction; do not insert an Invitation or queue `inviteMember` anywhere else. `POST /invitations` takes invite objects only. See the Waitlist registration row in `docs/agents/where-to-look.md`.

Member Announcements (ADR 0028) are committee emails to all members, BCC'd and sent through Resend's batch API as inline HTML. They are deliberately not Email Kinds: React Email generates gitignored `apps/phoenix/priv/email_shells/` artifacts before Phoenix compilation. Phoenix mise tasks and CI generate automatically; direct Mix/Docker builds need `mise run email-shells` first. Fly deployment generates on the runner before uploading the Docker context, so keep the artifacts out of `.dockerignore`. The body is a Tiptap JSON document that Phoenix renders from a closed vocabulary, and the live preview is Phoenix's render. See the Member Announcement row in `docs/agents/where-to-look.md`.

Beginners' Workshop Intake Emails (ALE-377) are the opposite choice: two Email Kinds (`beginnersWorkshopAction`/`beginnersWorkshopNotice`) whose `MESSAGE_HTML` variable is a club-wide template filled at queue time. Queue them only through `Dhc.BeginnersWorkshops.IntakeEmails.queue/4`, which renders the shared `Dhc.Email.RichText` vocabulary without inline styles, seals the Intake link, and passes the subject override. The 2,000-character measure must keep matching `packages/email-templates/fixtures/intake-email-measure.json`, which the dashboard counter shares. See the Intake Email row in `docs/agents/where-to-look.md`.

The Intake Email template editor (ALE-383) saves through `IntakeEmails.update_template/2`, whose refusals are named reasons (`placeholder_not_allowed`, `template_too_long`, `invalid_template`). Its browser counter (`lib/beginners-workshops/intake-emails/measure.ts`) must keep rendering exactly like `Dhc.Email.RichText` without styles: change both together and keep the shared fixture cases passing on both sides. The editor chip is `RichTextEditor`'s `placeholders` prop; never emit `{{name}}` text into a body. See the template editor row in `docs/agents/where-to-look.md`.

Invitation pricing tiers use backend-applied Stripe coupon IDs, not customer-facing promotion codes; see the invitation pricing tier note in `docs/agents/notes.md` for coupon configuration and E2E conventions.

Target Inventory Item operations live on `/api/inventory/items*` under the one `Inventory` tag since ALE-289 deleted the legacy slice and moved them onto the freed URLs (slice `inventoryItems.*`); those reads are operator-only by design. The member-facing catalog and own-loan operations (`/api/inventory/catalog/items*`, `/api/inventory/loans/mine*`) are a **separate read model**, not a role variant of the operator viewer — member rows cannot express container, notes, or maintenance facts at all. See the Inventory Item and member catalog rows in `docs/agents/where-to-look.md` before editing the API contract.

The generated API client carries a pnpm patch on `@hey-api/openapi-ts` (`patches/`, recorded in `pnpm-workspace.yaml`): ky v2 eagerly consumes error response bodies into `HTTPError.data`, so the unpatched generated client throws `TypeError: body stream already read` and every `error.errors?.detail` UI falls back. The patch reuses the pre-parsed body through the same interceptor pipeline; `pnpm --filter @dhc/api-client api:generate` (and postinstall) regenerate with it applied.

Every availability-changing inventory command — member request/cancel, operator approve/reject/cancel/checkout/return/date edits, move, maintenance open/close, archive, restore — is implemented **once** in `Dhc.Inventory.AvailabilityCommands.execute(actor, command)` (GH-508, ADR 0023): one private `with_locked_item/2` encodes the lock protocol (container chain `FOR SHARE` root-first, then item `FOR UPDATE`, then loans; a restore peeks only to learn which chain to share-lock and retries from a fresh peek if the container moved) and the re-read under the lock, one `persist/1` translates every partial index and principal FK into a domain reason, and the actor (`{:operator, id}` / `{:member, id}`) is authorized before any read. `OperatorItemLifecycle`, `OperatorLoans`, and `MemberLoans` are facades with unchanged signatures; add a new transition as a `run/4` clause in the boundary, never as a new `Repo.transaction` in a facade. `LoanPolicy` (pure predicates) and `LoanProjection` (operator/member views) are shared by the commands and the queue so advisory readiness and authoritative gates cannot diverge. See the availability-command row in `docs/agents/where-to-look.md`.

Every transaction that starts, concludes, cancels or refunds a Workshop payment — member/external start and completion (Registration or compensating Refund), member cancellation, requested Refunds, the Refund fan-out of `cancel_workshop`, Refund submission, Stripe `refund.*` events, reconciliation — is implemented **once** in `Dhc.Workshops.PaymentCommands.execute(actor, command)` (ALE-340, ADR 0027): one private `with_locked/2` encodes the lock order Workshop → Payment Attempt → Registration → Refund (skip levels, never lock upward; Refund-started commands peek unlocked, lock what the Refund points to, re-read and retry, and never take the Workshop lock), Stripe is called only between transactions and its result written after an authoritative re-read under that lock (idempotency keys `workshop-payment-attempt:<id>` / `workshop-refund:<id>`, no lease), one transition table writes every Attempt/Refund status (terminal Refunds ignore later events), and `persist/1` translates the unique indexes into `:already_requested`/`:already_registered`. `Dhc.Workshops` keeps the public functions and delegates; the refund workers only turn job args into a command; `Dhc.Workshops.Refund` is a schema only; refund eligibility predicates live in `Dhc.Workshops.RefundPolicy`, shared with the advisory `refund_eligibility/1`. Add a new payment rule as a `run/2` clause in the boundary, never as a new `Repo.transaction` in `workshops.ex`. See the Workshop row in `docs/agents/where-to-look.md`.

Loan commands are split domain-seam-first: the boundary writes every transition as durable rows and emits **no notifications**. The HTTP exposure (ALE-298) attaches keyed notifications *after* the command returns via `Dhc.Inventory.notify_loan_transition/2` → `create_keyed/3`. Wiring `Dhc.Notifications.create/2` into a loan transition is the specific mistake that split exists to prevent. See the operator loan and operator-loan-exposure rows in `docs/agents/where-to-look.md`.

Web Push (ALE-299, ADR 0025) is a **best-effort channel after the notification row**, never a second source of truth: `Dhc.Notifications.signal_created/1` broadcasts *and* enqueues one `Dhc.Notifications.Workers.WebPushWorker` job (Oban queue `:notifications`, `max_attempts: 1` on purpose — a job retry would re-push to browsers that already succeeded) per committed row, and neither can reach the creator. Subscriptions live in `Dhc.Notifications.WebPush` **per browser installation** (endpoint-unique upsert; 404/410 deletes the row) and the API discloses only the VAPID public key, `{id, createdAt}`, and `{removed}`. `web_push_ex` builds the RFC 8291/8292 request and Req sends it (`WebPush.Sender` behaviour, substitute with `:web_push_sender`). VAPID is optional and all-or-nothing via `WEB_PUSH_VAPID_{PUBLIC_KEY,PRIVATE_KEY,SUBJECT}` (generate with `mix web_push_ex.vapid`; unset = `enabled: false`, no jobs); tests use the fixed pair in `config/test.exs`. On the web side `apps/web/src/lib/notifications/web-push/` is pure and `PushManager.subscribe` — the only prompting call — runs only from the toggle click; Playwright's Chromium reports notification permission as denied unless a test grants it, so E2E only sees the "blocked" explanation. The `notifications:self` channel alias must subscribe to the principal's canonical PubSub topic or open dashboards receive nothing. See the Web Push row in `docs/agents/where-to-look.md`.

Notifications that can be retried must go through the keyed seam `Dhc.Notifications.create_keyed/3` (ALE-287), not `create/2`, which stays at-least-once for existing unkeyed callers. `create_keyed/3` refuses an open transaction because it signals after its own commit; a caller that already holds locks uses `create_keyed_in_transaction/3` and calls `signal_created/1` only after the outer transaction returns `{:ok, _}`. The key names the logical event; uniqueness is `(principal_id, notification_key)`, so one event notifies many recipients from one key. Loan reminders (`Dhc.Inventory.LoanReminders`) treat the durable ledger **as** the schedule rather than scheduling a job per reminder: one pass computes at most one owed occurrence per loan, so delivery and reconciliation are the same code path and a missed tick self-heals. `due_on_revision` is derived from the loan's due date, which is why a due-date edit reschedules reminders without any write on the transition path — the reason loan commands stay reminder-free. Inventory-operator eligibility (active profile + the `inventory.manage` capability) lives in `Dhc.Auth.Capabilities` (`principal_ids_with/2` and `authorize/3`); `RequireSession` and loan notifications both call it, so a leftover role row on an inactive principal cannot hear about loans the plug would 401. See the keyed-notification and loan-reminder rows in `docs/agents/where-to-look.md`.

The operator loan queue (`Dhc.Inventory.OperatorLoanQueue`, ALE-297) is a lock-free, actor-free **read model** over those rows: bucket counts are `length(rows)` of the bucket beside them rather than a second aggregate query, so the queue is deliberately unpaginated. It projects loans through `LoanProjection.operator_view/2` (the successor of `OperatorLoans.operator_view/2`) instead of rebuilding the shape, which is the rule to preserve when adding a bucket or field — a queue row and the operator detail read must not be able to disagree. See the operator loan queue row in `docs/agents/where-to-look.md`.

`mix gen.controllers` scaffolds one controller + JSON renderer + contract test per **slice** — the `operationId` prefix — not per tag, so a domain keeps one tag and one URL root while being served by several controllers (the `Inventory` tag owns `inventoryStructure` and `inventoryItems`). Every operation needs an `operationId` of `<slice>.<action>` whose prefix underscores to the controller filename, and `mise run api-gen` must stay idempotent (only `skip` lines, no new files). See ADR 0003 and the `mix gen.controllers` gotchas in `docs/agents/notes.md`.

Every Beginners' Workshop write goes through **one** boundary, `Dhc.BeginnersWorkshops.execute(actor, command, opts)` (implemented in `Dhc.BeginnersWorkshops.Commands`; ALE-378, ADR 0029 amendment): one private `with_locked/2` whose levels are Beginners' Workshop → Waitlist entry → Intake → Carried Fee → payment → refund (skip levels, never lock upward; an unknown level raises), one transition table (`transitions/0`), one `persist/1`, and a `Dhc.BeginnersWorkshops.Clock` passed as `opts[:clock]` and read inside the lock (tests pass `Clock.fixed/1`). Actors are `{:staff, id}` (capability checked before any read), `{:intake_link, token}`, `:stripe`, `:system`; add a command as a `run/3` clause plus its capability in `@staff_capabilities`, never a new `Repo.transaction`. Stage, seats and alerts come from the pure `WorkshopPolicy` over `WorkshopFacts` (the one place later tickets add paid/hold/Batch/Staff facts), shared by the boundary and the lock-free `WorkshopList`. It never touches Workshop storage: Reach forbids `Dhc.BeginnersWorkshops ↔ Dhc.Workshops`/`WorkshopAnnouncements` and `Waitlist`/`Onboarding` → BeginnersWorkshops (web slices too), and an `apps/web/.oxlintrc.json` override forbids Workshop ↔ Beginners' Workshop frontend imports. See the Beginners' Workshop rows in `docs/agents/where-to-look.md`.

Automatic Batches (ALE-380) are a time-driven `:system` pass, never a coordinator action: `send_due_batch` runs only through the one sweep (`Dhc.BeginnersWorkshops.run_due_passes/1`, `SweepWorker` every 5 minutes), decides with `WorkshopPolicy.batch_due?/3` under the workshop lock, and contacts the live `BatchProposal` — the same module the console's Next Batch preview reads. Add later time-driven passes (cutoff, finalisation, follow-up) to `run_due_passes/1`, not as scheduled jobs. Coordinator alerts go to the recipients-only `beginners.workshops.alerts.receive` capability. See the automatic Batches row in `docs/agents/where-to-look.md`.

Intake payment (ALE-381) is seat-capped through Seat Holds: seats taken = Intakes `paid` + payment rows `open`, and only Stripe ends a hold (`checkout.session.expired`, or `reap_holds` in `run_due_passes/1` asking Stripe to expire it) — never our clock. `start_payment` takes the hold under the workshop lock and calls Stripe only between transactions through `IntakeCheckout` (idempotency key `beginners-intake-payment:<row id>`, parameters derived from the row); Stripe-started commands find the row by Checkout Session id and lock top-down. The public page (`/beginners/intake/<token>`, Phoenix `/api/beginners/intake/:token`) is a closed safe view; the token must never reach a log, Sentry or PostHog (`DhcWeb.IntakeLinkPrivacy`, `#lib/intake-link-redaction.js`), and every response sends `Referrer-Policy: no-referrer`. The Stripe webhook endpoint must be subscribed to `checkout.session.completed` and `checkout.session.expired` in test and live mode. See the Intake payment row in `docs/agents/where-to-look.md`.

The Payment Cutoff pass (ALE-385) is `pass_payment_cutoff` in `run_due_passes/1`, after `reap_holds`: paid Intakes get "Pre-workshop info" once (log occasion `pre_workshop`), and each `contacted` Intake is settled only by `WorkshopPolicy.cutoff_settlement/3` — `lapsed` (standing `removed` via `change_standing/2`) with a seat free, `returned` (standing untouched) when full, and left alone while its own Seat Hold is open, because the cutoff stops only new holds. A person paid after the cutoff gets Pre-workshop info inside `complete_payment`. Change the live-hold reading in that one function. See the Payment Cutoff row in `docs/agents/where-to-look.md`.

Beginners' Workshop Staff (ALE-379) are the first **assignment-scoped** capability: `beginners.workshops.run` is granted to the managers by role and to a workshop's Staff by `assigned_principal_ids`, a denial conceals the workshop with 404, and router pipelines cannot use it, so controllers check it (the door controller against `DoorView`'s resource). Staff change only through the `set_staff` command (or optional Staff on `schedule_workshop`); its keyed Notifications are signalled after commit. See the Staff row in `docs/agents/where-to-look.md`.

Fast-track (ALE-384) is the `fast_track` command on the same boundary: it places a `waiting` person, a `removed` one within retention (restored via `Dhc.Waitlist.restore/2`) or a new person (via `Dhc.Waitlist.add_person/2`, inside the command's transaction) as a `contacted` Intake with origin `fast_track`, sharing the Batch path's one `contact/6` so the Contact email's `{{windowEnd}}` is the Payment Cutoff. Do not add a second Intake-creation or Contact-email path. See the Fast-track row in `docs/agents/where-to-look.md`.

## Navigation

Training Announcement lifecycle, drivers and first-freeze stamping (ALE-323/325/326) share `Dhc.TrainingAnnouncements.Store.with_current/2` for conditional-write claims and authoritative rereads. `Execution.evaluate/2,3` (ALE-348; the optional third argument is the driving job, which workers pass) is the only path from a due `{:announcement, id, date}` / `{:holiday, phase, date}` to its one Evidence row (one private `insert_all` writer, due-mode resolution, copy/channel checks) and the only caller of `Delivery.progress/3`, which owns post-commit Discord progression and maps `Dhc.Discord`'s classified failure atoms; `Scheduling` alone writes Oban jobs, and workers only turn job args into an `evaluate` call. `Execution.clock/0,1,2` is the one clock (Dublin today and `now_time` from `ClubCalendar`, holiday set) for execution and `OccurrenceReads`; Execution re-reads its time inside each claim, so decisions and stamps never use a pre-claim instant. Tests pass `clock: Execution.clock(fixed_now)`. Before changing these paths or Holiday Announcement recovery, read the Training Announcement rows in `docs/agents/where-to-look.md`.
